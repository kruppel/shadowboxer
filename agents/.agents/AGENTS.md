# AGENTS.md

## General

- Do not use emojis unless explicitly requested.

## Conversational Style

- No fluff or cheerful filler text
- Keep answers short and concise
- No emojis in commits, issues, PR comments, or code
- Technical prose only, be kind but direct (e.g., "Thanks @user" not "Thanks so much @user!")

## Code Quality

- Read files in full before making wide-ranging changes, before editing files you have not already fully inspected, and when the user asks you to investigate or audit something. Do not rely only on search snippets for broad changes.
- Don't be too verbose with comments in the code. Only write comments when there is serious ambiguity.
- No any types unless absolutely necessary
- Check node_modules for external API type definitions instead of guessing
- NEVER use inline imports - no await import("./foo.js"), no import("pkg").Type in type positions, no dynamic imports for types. Always use standard top-level imports.
- NEVER remove or downgrade code to fix type errors from outdated dependencies; upgrade the dependency instead
- Always ask before removing functionality or code that appears to be intentional

## Commits / Pull Requests

- When creating git commits, use simple, clean commit messages without any agent attribution, emojis, or co-authorship lines.
- Do not include Generated by Claude Code annotation in any pull request description.
- Bias towards conventional commit style. State the Linear issue as `Refs {issue_id}` in the commit body, if applicable. **Do not make up commit IDs**.
- Use `agents` as the scope for agent-related commits (not `operator`). E.g. `fix(agents):` not `fix(operator):`.

### Stacked PRs

- Default to 2–4 PRs per stack; split larger work into separate stacks or milestones. A stack must represent one user-visible capability, not the chronological sequence of implementation.
- Keep changesets small and digestible: target roughly 300–500 lines per PR. When a feature exceeds that, propose a stack before opening one large PR.
- Each PR must have one clear review decision, meaningful behavior or reusable foundation, and focused tests. If a reviewer must understand the whole stack to approve a PR, the boundary is wrong.
- Prefer dependency-ordered vertical slices over horizontal layers. Keep mechanical changes separate, and do not create a PR solely to enable the next one unless it establishes a reusable primitive.
- Build and live-test the complete feature on a reference branch first, then carve the stack by subtraction: each PR is a strict subset of the proven end state, single-concept, and independently green.
- The final PR's tree must be byte-identical to the reference branch (empty `git diff`) — that is the proof the stack reassembles what was actually tested.
- Behavior stays coherent at every level of the stack (e.g. a plain-prose fallback before the typed version lands) — never half-wired.
- Note "Stacked on #N; merge that first" in each PR; update earlier PRs' stack diagrams with real PR numbers as later ones open.
- Force-push only with `--force-with-lease`.

### PR description language

- Write PR descriptions and commit messages in plain language, one human talking to another. No internal jargon — "slice", "rung", "idiom", "status-discriminated", "materialize" — outside of literal code identifiers. Apply the same standard to diagram labels.
- Method for every PR body: compose the `show-me` skill (smallest visual that makes the key point clear, scoped to the PR's change) with the `wut` skill (`~/.agents/skills/wut/SKILL.md` — restate plainly, no jargon, one human to another) over all prose and diagram labels.

### PR description diagrams

- Include a small ASCII diagram (fenced `text` block) scoped to the PR's own change when it clarifies flow or shape — module layout, a decision branch, a data reduction. Keep it to what this PR touches.
- GitHub renders Mermaid in Markdown. For stacked PRs, add one Mermaid diagram showing the whole stack and each slice's scope, in every PR of the stack. At most one Mermaid diagram per PR.
- Diagrams complement the Summary/Changes/Verification prose; they do not replace it and do not excuse exceeding a repo's word budget.

## Code Style

- In code, do not leave trailing whitespace.
- Bias towards less verbose logging unless stated otherwise (i.e. stated purpose/goal is clear).
- Do not add comments unless asked. For non-trivial changes, pause and consider if there's a more elegant approach; if a fix feels hacky, rethink it. Share potential areas worth documenting based on complexity or need for additional context.

### TypeScript/React

- Naming convention for event callbacks: use `on${ActionName}` pattern (e.g. `onSubmit`, `onNewThing`, `onMouseEnter`).

### Ruby

- Use an eigen class (`class << self`) when there are multiple class methods. Otherwise, prefer `self.{method_name}` for single class methods.
- Prefer shorthand hash values where applicable (e.g. `{ key: }` instead of `{ key: key }`).

## Testing

- Bias towards less tests, maximal coverage.
- Test public interfaces, unless directed otherwise.

## Workflow Orchestration

### Plan Mode Default

- Enter plan mode for any non-trivial task (3+ steps or architectural decisions).
- If something goes sideways, stop and re-plan immediately; don't keep pushing.
- Use plan mode for verification steps, not just building.
- Write detailed specs upfront to reduce ambiguity.

### Subagent Strategy

- Use subagents liberally to keep main context window clean.
- Offload research, exploration, and parallel analysis to subagents.
- For complex problems, throw more compute at it via subagents.
- One task per subagent for focused execution.

### Self-Improvement Loop

- After any correction from the user: update `.agents/tasks/lessons.md` with the pattern.
- Write rules for yourself that prevent the same mistake.
- Ruthlessly iterate on these lessons until mistake rate drops.
- Review lessons at session start for relevant project.

### Verification Before Done

- Never mark a task complete without proving it works.
- Diff behavior between main and your changes when relevant.
- Ask yourself: "Would a staff engineer approve this?"
- Run tests, check logs, demonstrate correctness.
- When integrating against another service, read that service's actual contract — generated schema dumps, serializers, controller source — not docstrings or memory; docstrings drift.
- When a live local environment exists, finish with one real end-to-end run and cite it in the PR's Verification section. Mocked tests alone don't prove the wire shape.

### Demand Elegance (Balanced)

- For non-trivial changes: pause and ask "is there a more elegant way?" This takes precedence over speed.
- If a fix feels hacky: "Knowing everything I know now, implement the elegant solution."
- Skip this for simple, obvious fixes; don't over-engineer.
- Challenge your own work before presenting it.

### Autonomous Bug Fixing

- When given a bug report: just fix it. Don't ask for hand-holding.
- Point at logs, errors, failing tests; then resolve them.
- Zero context switching required from the user.
- Go fix failing CI tests without being told how.

## Task Management

1. **Plan First:** Write plan to `.agents/plans/` with checkable items.
2. **Verify Plan:** Check in before starting implementation.
3. **Track Progress:** Mark items complete as you go.
4. **Explain Changes:** High-level summary at each step.
5. **Document Results:** Add review section to the plan file.
6. **Capture Lessons:** Update `.agents/tasks/lessons.md` after corrections.

## Core Principles

- **Simplicity First:** Make every change as simple as possible. Impact minimal code.
- **No Laziness:** Find root causes. No temporary fixes. Senior developer standards.
- **Minimal Impact:** Changes should only touch what's necessary. Avoid introducing bugs.
